ARGUS Architecture

How ARGUS turns raw Linux logs from the lab into a triage decision an analyst can act on, how it learns new detection rules, and where it says plainly what its sensors could not see.

The whole workflow

Each lane has its own outline colour; lanes are numbered in the order data flows. The dashed grey lane is thesis evaluation only, never read by triage.

Stage by stage

1 · Lab capture

Real attacks on real machines

Four Debian victim VMs run ordinary admin and user activity. CALDERA, on a Kali VM, plays the attacker through an agent on each victim. Every victim records what it does with auditd and auth.log; a packet capture watches the network between them.

2 · Import

One folder per host per half hour

The analyst clicks Import capture in the workbench and picks a capture folder, or copies one in from their computer. ARGUS reads the audit logs, rebuilds which process launched which, and writes a window folder for every host and 30 minutes. It records what the sensor was set up to record, so a missing kind of event becomes a reported blind spot, and checks that the clocks agreed. With a CALDERA report, the run joins the evaluation in the order it was imported; without one, its cases are for triage only.

3 · Triage engine

A verdict that states what it could not see

  • Events become claims: typed facts with the process that did them.
  • The process tree links commands into stories; a login shell never joins two stories.
  • Hand-written and learned rules are scored against the claims.
  • Missing evidence counts against an attack only if the sensor was able to see it.
4 · Analyst workbench

Everything in the browser

Captures come in through Import capture. Cases arrive ranked by priority. Each case shows the verdict, what ARGUS could not see, the evidence, the process tree and a timeline. The analyst records a verdict, reviews coverage, and runs rule learning from the Rules page. No terminal is needed.

5 · Rule learning

The model proposes, the checks decide

ARGUS shows a language model process trees that are new to a host, with attacker text fenced off and identities hidden. Each rule it writes must pass five checks without labels. Rules no independent source confirms wait for the analyst to approve them.

Thesis evaluation

Graded once, on runs it never learned from

Ground truth comes from the CALDERA report and is used only for grading. The first three runs are for learning, later runs are the test, in the order they were imported, and every result names the frozen code it was produced with.

Inside one decision

A learned rule's life

The five checks a learned rule must pass

They run in order and stop where a rule fails; a check never reached is not counted as failed. A rule is shadow only with C1–C4 passed and active only with C5 passed.

CheckQuestion it answersWithout labels because
C1 validCan ARGUS run the rule as written?It reads only the rule.
C2 own evidenceDoes the rule fire on the episode it was written from, using values that really occur there?It reads only that episode.
C3 robustDoes it still fire when the attacker renames their programs, runs them by full path, or renames the files they create?The renamed copies are made from the telemetry itself.
C4 quietDoes it stay silent on at least three quarters of this host's other windows?Most of a host's history is ordinary activity.
C5 confirmedDoes a source that may decide on its own flag the same events: a deciding hand-written rule or a dated community Sigma rule rated medium or higher, each itself quiet on that host, or the analyst?Agreement with another model-written rule is noted and never counts. Your approval is recorded as the C5 pass.
